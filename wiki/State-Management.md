# State Management & Work Queues

A primary challenge in multi-session AI development is maintaining a consistent **work queue**. If an agent gets lost in a massive codebase, it may try to re-implement already completed components or leave features half-implemented.

SpeQ solves this by utilizing **State Tracking Files** (`state_[name].speq`), which act as an active, machine-readable work queue for your project.

---

## 📂 The State File Structure

A state file is automatically generated by running `speq check [file.speq]`. It lists every declared Entity, Layer, and Flow alongside its implementation status.

An example `state_main.speq` looks like this:

```speq
STATE 0.3.0

ENTITY
  user         BUILT     # Completed in Session 1
  product      BUILT     # Completed in Session 1
  cart         PARTIAL   # In progress, needs update_quantity
  order        PENDING   # Not started
  payment      PENDING   # Not started

LAYERS
  FRONTEND     PARTIAL   # Cart view pending
  BACKEND      BUILT     
  STORAGE      BUILT     

FLOWS
  checkout     PENDING   # Blocked by order/payment implementation
```

## 🔄 The State Management Loop

When working with an active state queue, enforce the following workflow loop:

### 1. Read State on Session Start
The AI assistant must scan the `state_[name].speq` file during initialization. The **[SpeQ Skill](file:///C:/Users/maertzdorf/OneDrive/GitHub/speq/SKILL.md#L138-L149)** strictly forbids agents from modifying or re-implementing any item marked `BUILT`. They must only focus on `PENDING` or `PARTIAL` tasks.

### 2. Implement the Target Feature
The agent writes the code required to transition a `PENDING` feature to `BUILT`. For example, implementing the `order` entity and database mapping.

### 3. Verify Constraints
Before updating the state, the agent runs validation checks:
*   Does the new code violate any `CONTRACTS`?
*   Are all variable names strictly conforming to `VOCABULARY`?
*   Has input sanitization been applied at the `BOUNDARY external` layer?

### 4. Transition State
Once verified, the state file is updated by changing the status to `BUILT` or using the SpeQ CLI tool:

```bash
# Update state via CLI
speq state set order BUILT
```

By systematically working through this state loop, you prevent duplicate work, ensure a highly linear feature rollout, and maintain complete alignment between your spec and your codebase.
